# 0066. One desktop app: agentes.chat, your own server, or a server here

- Status: Accepted. Built: the first run, the server list, links, agents here for your own server, Preferences by mode, Windows and Linux builds, and agentes.chat on this computer (§7). Amended 2026-10-26: Windows gets what a Mac has, agents here and agentes.chat on this PC (§5–§7). Superseded in part by ADR 0077 (2026-10-28): §8, coming from the menu bar app. With no `servers.json` the app starts with an empty list and shows the first run; homes a terminal install's `agentes-runner host` keeps are still never started unless they are the server here's own (§7). Superseded in part by ADR 0165 (2026-11-09) for the devices people bring: §3's "a link never pairs this computer" (a link may, after the person confirms in the app) and §4/§5's agentes.chat as a plain client (the app pairs this computer with agentes.chat too).
- Date: 2026-10-25
- Supersedes: ADR 0036's menu-bar-first model, its "the runner ships and starts in every install", and §11's "the main window loads agentes.chat only"
- Extends: ADR 0025 (connected computers), ADR 0035 (phone app, connect links), ADR 0036 (desktop app), ADR 0060 (one-command install)

## Context

The desktop app began as a menu bar app that let agents use this Mac: its first run signed the Mac in with a device code, it always started the runner, and its main window loaded agentes.chat only. Two things changed. agentes.chat Cloud gives every workspace a computer of its own, always on, so the Cloud no longer uses people's computers. And self-hosting is entirely the person's own: their server, database, files, computers and AI accounts, with no agentes.chat account and no sign-in with us. People on both need one app that is first a good client, on macOS, Windows and Linux, and only on a self-hosted server also a computer for agents.

## Decision

### 1. One app, the Cloud first

- The first run (the welcome window) has one big action, "Sign in to agentes.chat" (with "Create an account"), and a small line under it, "Use your own server". Nothing on that screen loads agentes.chat: it is the app's own page, so a self-hoster's first run contacts us for nothing but the app's update check.
- "Use your own server" leads to its two ways, "Connect to my server" and "Run agentes.chat on this Mac" (§7; in builds that carry the server; without it, straight to Connect): an address (the same one the person opens in the browser), servers found on this computer (named "This Mac") or the person's Tailscale network, and, for a server that has none yet, "Don't have one yet? Run this on it" with the one-command install (ADR 0060) and Copy. The one-command install works from a clean machine only once the repository, the setup package and the image are public: until then one constant (`INSTALL_COMMAND_LIVE`) hides "Run this on it".
- Connect follows ADR 0035's checks (`checkServer`: `GET /api/instance`, the server's own address when it differs). Plain http is accepted only for this computer's own loopback (`normalizeServer(…, { allowHttp: "loopback" })`); everything else stays https, so the app never sends a session over a network in the clear. There is no scan of the local network: servers listen on their own machine, and the tailnet and this computer are where they are found (`discover`: `~/.agentes/server.json`, ports 4310 and 3000, `tailscale status --json`'s `agentes.<tailnet>` and online devices named `agentes…`, at most 5).
- A server that waits for its first account through an owner link (`ownerClaim` in `/api/instance`, ADR 0060 §6) is not entered: the app says to open its owner link.

### 2. The servers this app opens

- Rust keeps a list and the current one (`servers.json` in the app's config folder). The main window loads the current server; switching keeps each server's sign-in, since cookies are per origin. The list is in Preferences › Servers (Open, Remove), in the menu bar's Servers menu on a Mac, and in the tray's menu on Windows and Linux.
- agentes.chat's pages get the capability in `capabilities/main.json`; any other server's get the same one, added at runtime for that origin only (`CapabilityBuilder::remote("<origin>/*")`, once per origin). Navigation rules are the same against whichever server is open: its pages stay, `/desktop/sign-in` goes to the browser, everything else opens outside, except the frame of the sign-in pages' bot check (Cloudflare Turnstile, `https://challenges.cloudflare.com` only), which stays in the page: on macOS and Linux the web view asks about frames too, so sent outside it would open a browser tab on every sign-in page and never load (a Rust test holds the rule).
- A page of a server in the list (an agent's browser request, an organization's page from the menu bar) opens in the main window, switching to that server. The only pages that open in the browser are the providers' sign-in pages and the app's own downloads.
- `window.__agentesDesktop` carries `platform` (`mac`, `windows`, `linux`): the site keeps room for a Mac's window buttons only there, and names this computer in its words ("Use this Mac", "Use this computer").

### 3. Links

- The app registers `agenteschat://`, the scheme the phone app and every QR code already use (`tauri-plugin-deep-link`; on Windows and Linux a link reaches the running app as a second launch, through the single-instance plugin's `deep-link` feature, and an AppImage registers the scheme at start).
- `agenteschat://connect?server=…[&token=…][&claim=…]` (`parseConnectLink`: a token or claim of 20 to 200 URL-safe characters, the whole link at most 2 KB, other parameters ignored) shows the server in large type, with a chip for Tailscale or this computer, and asks before anything changes: "Connect the app to this server?", with "You leave … in this app. Your account there stays." when another server is open. A link to the server already open just brings the window forward. A token ("Sign in to this server with your account from the other device?") opens `/desktop/handover#token=…`, which takes the token out of the address and the history at once and trades it at `POST /api/auth/sign-in/one-time-token` for a session of the window's own. A claim, while the server waits for its owner, opens `/owner#claim=…`. Anything else: "This link isn't from an agentes.chat server."
- A link never pairs this computer, starts a server or installs anything. One-time secrets travel only in a URL fragment, to their own server, and Rust passes on only `/login`, `/signup` or those two pages after a server's origin (`page_path`).

### 4. agentes.chat is a plain client

- With agentes.chat (or any server whose agents work elsewhere) nothing of this computer runs or shows: no runner starts (the app spawns runners only for homes on disk), no pairing, no folders or tools, no computer words. On a Mac the menu bar icon is off then (the Dock carries the badge) and "Show in the menu bar" turns it on. The app is always in the Dock, as a regular app: the bundle is not a menu bar only one (no `LSUIElement`) and nothing takes the icon away, since an icon that depends on a switch at runtime left some Macs with no Dock icon and no way to keep the app in the Dock. Windows and Linux have no Dock and closing the window only hides it there, so the tray icon is always on, with a native menu (Linux's AppIndicator passes no clicks to the app); on Linux, where some desktops show no tray, closing the main window minimizes it.
- Preferences shows General, Servers and Updates; this computer's tabs (Folders, Tools, Activity, Advanced) only while agents work here.
- The site's notifications (mentions, direct messages, what waits for the person: what a phone gets pushed, ADR 0035 §4) show while the window is in the background (`this_mac` `notify`): at most one every 3 seconds and 60 an hour, title 80 and body 180 characters, a path of the same server, which opens when the notification is clicked. "Let me know about messages and requests" turns them off. Amended 2026-11-11: the path was first opened by any return to the window within 30 seconds of a notification, which threw people out of the conversation they were in when they came back by the app's icon or Alt+Tab; now only the click opens it, and the path is the message itself (the inbox's own `openTarget`), the inbox only for what has no page of its own.

### 5. Agents on this computer, for your own server

- Only for a server of the person's own (`agentsHere`): never for agentes.chat (each workspace has a computer of its own), a server on this computer itself at any of its addresses (a loopback one, the server here at either of its own, or one whose loopback port here answers `/api/instance` with the page's origin as its `url`: its own computer is set up with it, ADR 0060 §3). The site hides "This Mac" wherever the app says no; an app from before this answer allowed it everywhere.
- The way in stays the site's one click ("Use this Mac" in the onboarding and in Settings › Computers). Before any page pairs this computer, the system's own dialog asks: "Let agents of {org} work on this Mac? {host} asked. They start with no folders of yours and commands off; you choose more in Preferences." The host comes from the app (the page's own origin), the organization's name from the page (display only). Then the runner pairs with that page's own server and the site confirms the code with its own session; nobody reads a code.
- `this_mac` answers about the asking server's own homes only: Rust adds the page's origin and `agentsHere` to every request it relays, and refuses `connect` where `agentsHere` is false.
- A first organization starts with the browser on, Claude Code and Codex on when found here, and commands off; another one copies the tools the others have, except commands, which every new organization starts without: a page asked for the pairing and the dialog promised it, and commands are granted only in the app's own Preferences (ADR 0036 §11). Preferences › Tools keeps one switch per tool for the whole computer; commands read on only when every organization has them, and otherwise name the organizations that do. "Reconnect this Mac" (an organization that refused it) opens that organization's Computers settings, where pairing again brings the same computer back (ADR 0036 §5).
- A server on this computer (plain http on loopback) is opened at the address it gives itself (`checkServer` follows an http `PUBLIC_URL` on loopback, as `http://localhost:3000` for the one-command install's `--network local` asked at `127.0.0.1`): its sign-in, realtime and pairing accept only that origin.

### 6. Platforms and builds

| | agentes.chat | Your own server | Agents on this computer |
|---|---|---|---|
| macOS (universal, 11+) | yes | yes | yes |
| Windows (x64, NSIS) | yes | yes (https, or `localhost` for a server in WSL 2) | yes, as the person |
| Linux (x64, AppImage and deb) | yes | yes | yes, as the person (the system mode with screens is the server install's, ADR 0057) |

- `desktop.yml` runs one job for the version, one for the server's files (§7, built once on Linux: JavaScript and WebAssembly, the same for every system), three builds (macOS universal, signed and notarized; Windows, unsigned for now; Linux on Ubuntu 22.04 for an older glibc) and one publish job; a test build (`release: none`) can take one system (`platforms`). Every build ships the runner and agent-browser: `tauri.windows.conf.json` makes the NSIS installer from our copy of Tauri's template (`src-tauri/installer/installer.nsi`, each change marked: Welcome, Installing and Done, no folder to choose, an upgrade over the older version without asking, English and Brazilian Portuguese, the pictures drawn by `scripts/installer-art.ts` at twice their size; the update still shows only the progress), with the runner compiled for `bun-windows-x64-baseline`, and the Windows job runs the server's files once before the build (`apps/desktop/scripts/server-smoke.ts`: it answers, and it stops as the app stops it there); `tauri.linux.conf.json` makes the AppImage and the deb, with the runner compiled for `bun-linux-x64-baseline`; the Linux job also runs the server's files once, checks the deb carries the sidecars and the server's files, and opens the AppImage on a virtual screen as a first run and on agentes.chat (it must still run after 25 s; the screenshots go up as `desktop-linux-look`). The app sets `WEBKIT_DISABLE_DMABUF_RENDERER=1` on Linux unless the person did: WebKitGTK's DMA-BUF renderer leaves the window blank with NVIDIA's driver, in virtual machines and in many AppImage setups. The publish job takes only the three builds' artifacts. Its jobs hold the signing keys, so every action is pinned by commit, as in `ci.yml`.
- The server's release reader learns the three targets (`desktopAssets`): Windows' installer is its own updater bundle; on Linux the deb is the download and the AppImage updates itself. The updater's address names the bundle the app came in (`bundle={{bundle_type}}`): only an AppImage is sent the AppImage, and a deb is told there's nothing to install, so it downloads the new deb instead. A release without a platform's files leaves that platform on the newest release that has them. The release list is read once in 5 minutes for every platform.
- A self-hosted server has no builds of its own (no `DESKTOP_RELEASES_TOKEN`): its download button asks agentes.chat's public answer, without the page's cookie.

### 7. agentes.chat on this computer

"Run agentes.chat on this Mac" ("on this PC" on Windows, "on this computer" on Linux) runs the native server (ADR 0060 §2) inside the app, for a person or a small team while this computer is on; the screen says so, and that a bigger team or an always-on server uses the one-command install, where the data can move later.

- **The server comes with the app.** Every build carries the server's `server/` and `web/` folders among their resources (`desktop.yml` builds them from the same commit; `tauri.native.conf.json`), signed and notarized with the app, so nothing downloads. On the first start of each version they are copied into `~/.agentes/app/<version>` (`app/current` points at it, a link, or on Windows a file naming the version; the previous copy stays), and the app runs `server/native.js` with the runner binary it already ships, acting as Bun (`BUN_BE_BUN=1`), with only the variables it needs (and on Windows the ones Windows itself needs, `WINDOWS_ENV`): a person's shell can't override the folder's settings. No program the app starts opens a console window on Windows (`no_console`).
- **Setting it up** asks the owner's name (from this computer's account) and email, reach (off) and usage statistics (on), then runs, each step on screen: the folder (mode 700) and its settings, made by the app (`AGENTES_SECRET`, a free port from 4310, `PUBLIC_URL`, the owner key in `owner-key` with its SHA-256 as `OWNER_KEY_SHA256`, `HOST_COMPUTER_TOKEN` in `.env` and in `host-computer-token`, `TELEMETRY`, `INSTALL_MODE=desktop`; secrets mode 600), and the database (`migrate`); the start (`/api/health` within 3 minutes); the owner (`POST /api/auth/owner-key` with the name and email: no password, ADR 0060 §6); this computer as the agents' computer; reach, when asked. Then the main window opens there, signed in through `/desktop/handover`, on the onboarding, and Open at login turns on. The steps sit in the window's middle under this computer's portrait. A step under way shows its time from 10 seconds, and from 30 it says it is taking a little longer than expected, with Copy details. Every wait has a limit: the database 3 minutes, the start 3 minutes, the owner 17 seconds, this computer 1 minute (it never stops the setup, and the minute's sync finishes it), reach 20 seconds and a restart (a warning, never a stop). A failed step says what happened on its line, with Copy details, Cancel and Try again. Cancel works at every step, and Esc presses it. What the setup started stops, and the database it made goes (the folder's `setup-pending` until its last step is done), so Try again and the next setup start it fresh. The folder's settings and the copy of the server stay. Open at login turns on, and `local-server.json` is saved, only when every step is done. Closing the window hides it while the setup goes on, and a notification says so if it then fails. If the last one-time sign-in fails, the window opens on the server's sign-in page, whose Continue on this Mac signs the owner in.
- **One already installed:** a native install from the terminal in `~/.agentes` (it has no owner key: it isn't the app's) that runs (its `server.json` names a live server of that folder), or an agentes.chat answering on this computer's port 3000, is offered as "Use it"; while a terminal install waits for its owner (its `owner-claim` file), and runs, "Use it" opens that claim's link sheet (§3). A terminal install that isn't running says so: it starts the way it was installed. The app never runs a server it didn't set up. While the app runs its own, "Run agentes.chat on this Mac" offers to open it instead of the form.
- **Only its own child is the server.** Other accounts and programs on this computer can listen on the loopback port. The app counts the server as running only when `/api/health` answers and `server.json` (written once it listens, in the folder only this person can write) names the child's pid; before spawning it checks the port is free and moves to the next free one otherwise (a taken port at start, exit 5, does the same). Until then nothing gets the owner key, `HOST_COMPUTER_TOKEN` (the host sync waits for it), the machine tokens of its host homes (they run only while it answers, and pause when it stops) or the main window's bridge: `this_mac` from the server here's origin is refused until it runs (a page that loaded as it came up waits up to 10 seconds).
- **The app supervises it.** It starts with the app (at login too), starts again after a crash (1 s doubling to 60 s), and stops gracefully (SIGTERM; it drains, 25 s at most) on quit, logout and before an app update. Windows has no SIGTERM: the app holds the server's stdin and closes it (`--until-stdin-ends`), which also stops a server whose app ended any other way, and kills it (`taskkill`) after the grace; its installer replaces the running programs' files and ends the app, so the runners and the server stop before it runs (the updater's `on_before_exit`); quitting asks first, since nobody can use it until the app opens again. A server left running by an app that ended without stopping it (the folder's lock names its pid, and its command line names the folder) is stopped first, before anything is copied (on Windows none is left: it stops with its stdin). Starts in a row that don't answer get 3 minutes in all, or three tries, whichever ends first: then "isn't starting", with Try again and Copy details (versions, state, the server's last lines, the setup's steps and the end of its log; no secret). Three stops in 10 minutes notify. A setup that is cancelled or fails leaves nothing running, shown, shared or started at login, and no database it made. The cover shows the time from 10 seconds when the server here starts or updates, and Copy details once it takes longer than expected (30 seconds starting, 2 minutes updating). An update's dump and restore get 30 minutes each. A server out of reach gets Use another server. The main window's cover says when it starts, updates, stopped or isn't starting, with the button that fixes it; the menu bar (the tray's menu on Linux) has its state, Start and Stop.
- **Its owner signs in with the app.** The owner key never leaves the app. `this_mac` `signIn` (only from the server here's own pages, one every 10 seconds) spends it on a one-time sign-in that the window trades at `/desktop/handover`; the site's sign-in offers "Continue on this Mac" there (`this_mac` `status` says `local: true`), also for an account with no password, which elsewhere is told to sign in from the app.
- **This computer as the agents' computer, with no code:** `agentes-runner host --once` (ADR 0060 §3) when the server answers, every minute, at once when the site reports a new organization (`orgs`), and with `--rotate` for a home its organization refused. Its homes (`managedBy: "host"`, pointing at the loopback address) run as the app's own runner children (`Runners::rescan`; a terminal install's host homes stay its service's) and start with the app's first tools (the browser on, Claude Code and Codex when found, commands off). The onboarding then picks "This server's computer" once it is online. Agents there run as the person (single-user, on Linux too), so the Commands warning names this agentes.chat's data.
- **Reach** is the person's own Tailscale (`tailscale serve --bg --https=443 http://127.0.0.1:<port>`, 8443 when this device already serves something else on 443; never Funnel): `PUBLIC_URL` becomes the device's tailnet address and the server starts again; its entry in the server list moves with it, and the window signs in again there with a fresh one-time sign-in. Pages of its homes, which keep the loopback address, open at that address. HTTPS or Serve off for the tailnet is said with "Turn it on" (the admin page Tailscale named), and Linux without the right to change Tailscale's sharing with the one command that gives it, to copy. Turning it on or off says each stage while it takes (`local-server://reach`: Tailscale sharing it, the restart at the new address, signing in again), under the switch in Preferences and under the setup's step. When Tailscale names its page for allowing HTTPS and waits there, the app shows that page at once ("Open Tailscale's page") and waits with it, 3 minutes at most, going on by itself once it is allowed, or ending at "Stop waiting"; the share tried again in the background never waits for anybody. While Tailscale's state is still being read (up to 2 seconds), the line under the switch says so. A server that doesn't answer again at its new address is said as that, with Copy diagnostics, not as Tailscale's refusal. Off: `tailscale serve … off`, and the loopback address again. Tailscale shares it only while it runs here: the share goes when the server stops (Stop, "Stop running it here…", quitting) and comes back once it answers again (tried every minute until Tailscale is connected), so the tailnet address never leads to whatever listens on the port meanwhile. With reach on, Preferences shows the phone's QR code (the site's "Open on your phone", `?open=phone`). On Linux, Tailscale is connected from the terminal (`sudo tailscale up`, to copy): there is no app to open.
- **Usage statistics:** the switch writes `TELEMETRY=on|off` into `~/.agentes/.env` (on by default; changing it restarts the server), beside `INSTALL_MODE=desktop`; the server's reporter reads them (ADR 0060 §5). The app itself sends no report.
- **Updates in lockstep:** the app's update carries the server. Before a new version's first start the database is copied to `backups/db-<previous version>`; a version that doesn't answer in 3 minutes, or three starts, goes back to the previous copy and that database, and says so. The app remembers it (`local-server.json`): later launches of that version start the previous copy, with the same banner, until the next version. A database of another Postgres major (exit 4) is upgraded with the previous copy's `db dump` and this one's `db restore`.
- **Preferences › Servers** has its card: state, address, reach (by what Tailscale is doing here), the phone, usage statistics, version, the data folder with Back up now (`backups/agentes-<date>.tar.gz` of the database, the files and `.env`, taken with the server stopped; the two newest stay) and Show in Finder, Restart, Stop, and "Stop running it here…" (it no longer starts with the app, and its organizations' agents stop working here; its data and their homes stay, and the app never deletes them). Afterwards the card says it doesn't run here, with "Start it here", which brings both back. Setting it up again from the first run keeps its usage statistics and reach as they were.

### 8. Coming from the menu bar app

On the first start of an app that keeps a server list (no `servers.json` yet), Rust reads the homes before any runner starts: homes paired with agentes.chat stop and go (their agents' folders stay; one notification says where), homes of an own server keep running and their servers join the list (the first by organization name is the one open), and homes a terminal install's `agentes-runner host` keeps in `~/.agentes-runner/orgs/` (`managedBy: "host"`; there only when given that `--state`, since on a Mac its own default is `~/.agentes-runner/host`, ADR 0060 §3) are never started by the app. The menu bar app's "Server: … · Change" choice opens as the current server.

## Consequences

- The app is a client first: people on agentes.chat get the workspace without anything running on their computer, on three systems.
- Self-hosters connect by address, by what the app finds, or by the setup's link, and their server is the only one the app talks to besides our update check.
- A server the person connected to is a website with a narrow bridge: its own homes, a native dialog for every pairing, notifications within limits.
- Running agentes.chat on this computer needs nothing else installed and no terminal, and moves with the app: one update, one signature, the server and the agents here always the same version. The cost is the app's size (the server's JavaScript and WebAssembly) and a server whose life is the app's: it runs while the app does.
- Until the first three-platform release, the screens are checked in a browser with the fake host and the Rust in a Linux container (the server here against the real server's files there); the macOS-only parts (the notch, the Dock, the menu bar) are compiled by the macOS build.
